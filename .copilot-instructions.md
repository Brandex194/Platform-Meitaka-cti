# Copilot Instructions - Sentinel AI

Queste istruzioni guidano GitHub Copilot nella generazione di codice per la piattaforma Sentinel AI.
Fonte di verita architetturale: `Architettura.md`.
Aggiornato il 9 novembre 2026 per il rebuild (codice in questa cartella). Stato reale del codice: `docs/STATO-PROGETTO.md`. Spec e piani del rebuild: `docs/superpowers/`.

## 1. Obiettivo progetto

Sentinel AI e una piattaforma di threat intelligence multi-tenant.
Non e un SIEM/SOAR/EDR: deve integrare sistemi esterni, non sostituirli.

Aree funzionali:
- Amministrazione: connettori, utenti/ruoli, policy, audit.
- Analisi: ricerca, correlazione, case investigation.
- Clienti: dashboard rischio, evidenze, report.

## 2. Scope MVP obbligatorio (Fase 1)

Copilot deve privilegiare solo questi blocchi:
- Collectors base: CVE, IoC, Leak.
- Normalizzazione e deduplicazione entita.
- Correlazione base con asset tenant.
- Scoring a livello asset con propagazione tenant.
- Dashboard cliente (score + trend principali).

Non introdurre come default componenti phase-2:
- Neo4j/knowledge graph dedicato.
- GraphQL completo.
- Feed enterprise avanzati non richiesti.
- Playbook SOAR automatici.

## 3. Stack tecnico vincolante

Usare prioritariamente:
- Backend: Python + FastAPI.
- Async jobs/enrichment: Celery con Redis broker.
- Queue/event stream: Redis Streams.
- Database primario: PostgreSQL 16.
- Cache: Redis 7.
- Frontend: React 19 + TypeScript + Vite, Tailwind, TanStack Query/Table, Recharts, Zustand, oidc-client-ts (nel rebuild non si usa shadcn/ui).
- Auth/SSO: Keycloak (OIDC/OAuth2).
- Runtime: Docker Compose (dev), K3s single-node (prod small-scale).

Evitare aggiunte non richieste (nuovi framework, nuovi DB) se non motivate da requisito esplicito.

## 4. Modello dati minimo da rispettare

Entita chiave:
- Tenant/Customer
- Asset
- Identity
- Vulnerability
- Indicator (IoC)
- Leak/CredentialDump
- PhishingDomain/TyposquatDomain
- Observation
- Source
- Score
- ScoreRule
- Case/Investigation

Relazioni minime:
- Tenant -> Asset, Identity, Score.
- Asset -> Vulnerability, IoC, Identity.
- Observation collegata a Source e entita osservata.
- Score collegato a ScoreRule e target (asset/tenant).

## 5. Scoring (non negoziabile)

Applicare queste formule:

- S_base(i) = f_severity(i) * w_severity + f_confidence(i) * w_confidence + f_recency(i) * w_recency
- S_context(i,a) = S_base(i) * E_exposure(a) * I_impact(a)
- R_asset(a) = min(1, somma(S_context(i,a) * alpha_i))
- R_tenant(t) = somma(R_dominio(t) * beta_d)

Pesi default:
- w_severity=0.5, w_confidence=0.3, w_recency=0.2
- beta: infrastruttura=0.40, leak=0.30, phishing=0.20, reputazione=0.10

Soglie livello rischio:
- 0.0-0.2: Low
- 0.2-0.4: Medium
- 0.4-0.7: High
- 0.7-1.0: Critical

Ogni modifica a pesi/soglie deve essere tracciata via ScoreRule versionata e audit log.

Dal 09/11/2026 il risk engine segue questa sezione (decisione dell'utente, "strada B"). Le formule stanno in `backend/app/risk/formulas.py` e i parametri nella ScoreRule (`weights`, `thresholds`, `parameters.formula`). Dal passo 5 la formula di default è `"architettura-5-moltiplicativa"` (S_base = gravità × (confidenza × 0.3 + recency × 0.3 + EPSS × 0.4), esposizione 1.0/0.7/0.3, impatto 1.0/0.7/0.4, ScoreRule globale v2); la formula additiva `"architettura-5"` resta valida per le regole che la indicano. Le regole senza `parameters.formula`, o con una formula sconosciuta, il motore le ignora. I 7 scenari del confronto e i 12 della taratura in `tests/test_risk/test_formulas.py` sono test di regressione (5 e 6 documentati come mancati): se cambiano, la modifica allo scoring va concordata. R_group e R_tenant non sono ancora implementati.

## 6. Regole implementative per pipeline

Pipeline logica obbligatoria:
1. Ingest collector -> topic `raw-observations`.
2. Normalizzazione + dedup.
3. Enrichment per tipo entita -> topic `enriched-entities`.
4. Correlation engine -> topic `correlation-events`.
5. Risk engine aggiorna Score asset/tenant + invalidazione cache.
6. Alert solo su superamento soglie/transizioni livello.

Per i collector:
- Implementare retry policy con backoff (preferibilmente esponenziale).
- Rispettare rate limit per sorgente.
- Validare campi obbligatori e formati.

## 7. Multi-tenant e sicurezza

Obblighi:
- Isolamento tenant su tutte le query dati.
- Row-level security su PostgreSQL quando applicabile.
- Nessun segreto hardcoded nel codice.
- Segreti gestiti via vault o variabili ambiente sicure.
- Cifratura in transito (TLS) e a riposo.
- Audit append-only per azioni amministrative e scoring changes.

## 8. Convenzioni di naming e API

Naming:
- Classi/entita: PascalCase.
- Funzioni/variabili: snake_case.
- Costanti: UPPER_SNAKE_CASE.
- Tabelle DB: lowercase plural (es. assets, observations).
- Topic: kebab-case (es. raw-observations, enriched-entities).

API:
- REST versionate (es. /api/v1/...).
- Contratti chiari con Pydantic schema.
- Error model consistente.
- Rate limiting per tenant.

## 9. Qualita minima richiesta

Ogni feature deve includere:
- Test unitari per regole di business (incluso scoring).
- Test che verifichino il contratto con il frontend sugli endpoint reali, non solo con mock MSW (oggi frontend e backend non coincidono).
- Test integrazione per pipeline principali.
- Logging strutturato con contesto tenant_id e correlation_id.
- Metriche minime: record ingestiti/scartati, errori, latenza pipeline.

Non produrre codice senza validazione input/output e gestione errori esplicita.

## 10. Indicazioni per output Copilot

Quando generi codice/proposte:
- Mantieni coerenza con Architettura.md sezioni 5, 6 e 9.
- Proponi prima soluzione MVP semplice e scalabile.
- Se una richiesta esce dallo scope MVP, segnala che e fase successiva.
- Non introdurre dipendenze pesanti senza motivazione tecnica chiara.
- Preferisci componenti sostituibili e configurazione YAML/JSON per regole.

In caso di ambiguita, privilegia:
1. Correttezza multi-tenant e sicurezza.
2. Tracciabilita scoring e audit.
3. Semplicita operativa small-scale.
4. Estendibilita futura senza rework massivo.
